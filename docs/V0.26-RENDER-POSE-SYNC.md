# v0.26 — Render-pose synchronization and reduced HDRP load

v0.25 confirmed that `MFPP.Player.LateUpdate` is available and the headset pose
is being applied there, but the user reported no meaningful reduction in
judder.

The remaining mismatch is deeper:

1. Unity renders the two eye RenderTextures using pose N.
2. Present occurs.
3. The OpenXR frame loop calls `xrLocateViews` again and obtains newer pose N+1.
4. The old eye images were being submitted while claiming they were rendered
   at pose N+1.

That prevents the compositor from correctly reprojection/timewarping the image.

v0.26 tags the exact pose applied in LateUpdate and submits the stereo
projection layer with that same render pose. The compositor can then compensate
from the old render pose to the latest headset pose.

The revision also disables the original desktop gameplay camera while true
stereo is active. Previously HDRP rendered:

- desktop gameplay camera;
- left eye camera;
- right eye camera.

Now gameplay normally renders only the two eye cameras. The original camera is
restored automatically for the pause-menu cinema fallback and when leaving the
gameplay scene.

## Replace

- `PluginInfo.cs`
- `XR/HeadTrackingPatch.cs`
- `XR/XrBackendManager.cs`
- `XR/OpenXrNativeBackend.cs`
- `XR/StereoCameraRig.cs`

No native probe rebuild is required.

## Expected log

```text
[HeadTracking] Patched MFPP.Player.LateUpdate for late head-pose application.
[StereoRig] Disabled desktop gameplay camera while stereo rendering is active.
[XRBackend] Submitting render-matched pose sequence=...
```

## Expected effect

Two independent improvements are expected:

- less head-motion judder because the projection-layer pose matches the pose
  used to render the eye images;
- fewer frame-time spikes because HDRP is no longer rendering the gameplay
  world a third time for the desktop while stereo is active.

Pause mode still restores the desktop camera before switching to the cinema
fallback.
